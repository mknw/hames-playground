# Should the Decide step see the conversation's documents? (Design note)

> **Status: design note, not built. The owner decides.** Nothing here is dispatched, and every identifier marked _proposed_ does not exist. Source claims were read on `origin/main` at `664c464a`; evidence is from [Eval run 3](https://github.com/mknw/hames-playground/issues/507#issuecomment-6281039851) (synthetic fixtures, private tier, one pass). It extends [`decision-loop-agent.md`](decision-loop-agent.md), which says what the decisions model sees ([What the decisions model sees each iteration](decision-loop-agent.md#what-the-decisions-model-sees-each-iteration)) and says nothing about documents. A security/privacy review is owed before any slice is dispatched; the [threat model](#threat-model) is written for that reader.

## The decision, in one paragraph

Today the decisions model choosing the next route is never told that a conversation holds uploaded documents, so a question that names an uploaded file by its bare name can be routed to the web instead of `read-documents`. **Recommendation: tell it, narrowly.** On a run that is explicitly on the private tier, show the name, type and size of an uploaded document **only when a user line already in the state names it**, plus a count of the others; on every other tier, show the count alone. This adds no name the decider has not already been sent, and it needs no new egress rule. It is **unmeasured**: the decider is a small classifier, one live sample is all there is, and the change is only worth building behind a live pass (see [Tests](#tests-and-mutations-a-builder-needs)). Scenario 13 is in the flip gate's must-set (run 3: fails 11 and 13), so until 13 passes the gate cannot be eligible.

## The problem and the evidence

The decide request is `{ model, state, questions }` (`packages/harness-baml/jev-decide.server.ts:299-305`). The state is built per iteration by `renderState` from three things only: the conversation window, one line per finished step this turn, and the last N route outputs in full (`packages/harness-patterns/patterns/decisionLoop.server.ts:361-385`, called at `:454`). The questions carry each route's description. No document list is part of either.

Run 3, scenario 13 (`two-sources`: "Compare the Project count in the knowledge graph with the target count in lantern-notes.md. How far apart are they? Cite the notes."). The conversation had `lantern-notes.md` and `lantern-sales.csv` in its stash. From the run's capture file (gitignored, synthetic):

| Decision | State the decider was given                                                                                                                     | Its distribution                                                                             | Choice           |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ---------------- |
| 1        | the user line, then `This turn so far: (nothing yet)` (324 input tokens, 144 ms)                                                                | info-retrieval 0.633, think 0.233, answer 0.086, **read-documents 0.025**, office-data 0.025 | `info-retrieval` |
| 2        | the same user line; `1. info-retrieval — succeeded`; its result: the graph has 42 projects and "lantern-notes.md" holds one line with no target | answer 0.743, **read-documents 0.166**, info-retrieval 0.066, think 0.013, office-data 0.013 | `answer`         |

What this shows:

- **Nothing in either state says the file is a conversation upload.** `lantern-notes.md` is a bare name that looks equally like a web resource, and the info route treated it as one: it web-fetched the name, got a one-line fixture page, concluded there was no target and answered with 42 only. Run 3 grades that a fail (answer lacks 50 and 8, no citation, `read-documents` never chosen).
- **The wording lever has already been pulled.** The route criteria in the capture are byte-identical in both decisions and already carry #697's text ("an uploaded file the user names without saying "uploaded" … also when an earlier knowledge-graph or web lookup did not find it"; `info-retrieval` says it cannot open uploaded files) (`packages/agents/agents/general-next.server.ts:215-229`). It did not move the distribution. That was #697's own stated risk: a wording hypothesis, unmeasured until run 3.
- **The passing neighbour differs by one word.** Scenario 12's message says "the **uploaded** lantern-notes.md … cite the **document**"; the #697 replay found that to be the one word the old `read-documents` criterion could match. A state line that says which files are uploaded supplies the same signal without relying on how the user phrased the question.
- **Scenarios that name uploaded files:** 09, 10, 12, 13, 14, 17 (and 15/16 once P4 ungates them). Only 13 fails on this axis in run 3; 09 and 10 did not run (stop threshold), so the effect on them is unknown.

What the evidence cannot show: one sample per decision; the decider is a 4B classifier reached through a self-hosted shim, and the Anthropic tier's decider (`JevDecide`, `packages/harness-baml/clients.server.ts:406`) has never been measured on this agent. It is not evidence that a state line would flip scenario 13. It is evidence that, as built, the decider cannot know.

## Options

All are _proposed_. "Disclosure" is what the decisions endpoint receives that it does not receive today.

| #   | What the decider is shown                                                                                                                                                      | New disclosure                                     | Fixes the 13 shape?                                                            | Main cost / risk                                                                  |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| 1   | every visible document's name, type, size (capped list)                                                                                                                        | **all names**, including ones never mentioned      | likely; unmeasured                                                             | the largest disclosure; names can carry identities and instructions               |
| 2   | a count only: "N documents in this conversation"                                                                                                                               | the fact that documents exist                      | partly: supplies "uploaded", not _which_ file; unmeasured                      | a count can bias every turn toward `read-documents` (a false-positive direction)  |
| 3   | nothing (status quo, plus more wording work)                                                                                                                                   | none                                               | tried, did not move 13                                                         | each wording round costs a live pass                                              |
| 4   | **names a user line in the state already contains** (name, type, size, searchable or not), plus a count of the rest. _Added by this note, beside the three first asked about._ | **none**: the matched name is already in the state | likely: ties the user's own word to "this is an uploaded document"; unmeasured | a lexical matcher; misses a paraphrase ("the notes"), where the count still helps |

**Alternatives that do not put names in the state:**

- **A. A `files` hint from the UI.** The composer sends the ids of documents it means; the server validates them against the caller's session index and renders them as in option 4. Strongest signal (intent, not lexical matching) and no matcher. But the wire has no such field (`app/src/routes/api/events.ts:38-41` takes `sessionId, message, agentId, mode, settings`), the stash is conversation-scoped with no "attached to this message" concept, a browser-supplied id is a new input to validate (SD-13), and triggered or routine runs have no composer. A sensible v2 on top of option 4, not instead of it.
- **B. A pre-Decide retrieval probe.** Run one vector search with the user's message before iteration 1 and show the top hit's source. It needs the document count first to skip empty conversations (so it subsumes option 2), costs an embedder call and a KNN query on every turn with documents, carries content-derived information (a hit) rather than a name, and with `EMBEDDINGS_PROVIDER=openrouter` would send the user's message off-box on every turn, adding the "embedder" exit that P4's table has to hold. Rejected for v1.
- **C. More description wording.** Cheap to try, costs a live pass to learn anything, and has already failed once. Fine as a complement.
- **D. The info route's own lever (adjacent, not designed here).** The info loop web-fetched a bare file name because nothing tells its controller that conversation uploads cannot be fetched (#697 recorded this as "a separate lever"). It has value even if Decide routes right, because "graph first" is a legitimate first move for a two-source question.
- **E. Force the route in code when a name matches.** Rejected: it overrides the decider the owner chose (G12), and a named file can legitimately be `office-data` (run code over it) or `info-retrieval` (the user gave a web address).

**Where the line is drawn in code (proposed).** Core never reads the tier, because the tier is an opaque string to it. The host's document source returns what the run may reveal: all it can see as a total, and a name list only when the raw tier is exactly the private one. Core renders whatever it is handed. So the policy is one reviewed function in the app's composition root, set in code, never by an environment variable (the same rule as `createWebPseudonymiser({ directory })`).

**Two rules that follow from P4.** (a) A document that P4's slice 5b tags `graph-file`, or marks `privateTier`, and that the person has not released to the Anthropic tier must be absent from the list on any non-private run, name and count both. The list should be exactly the set `read-documents` could return on that run. (b) A name that the user typed is the user's disclosure; a name the user did not type is the app's, and needs the tier line above.

**G14 does not cover names.** The roster covers people in labelled Graph fields and the directory, and wraps the `info-retrieval` route only. A file called "Review - Jane Roe.xlsx" is not in it. Nothing here pseudonymises a name; option 4 avoids needing to, by showing only names the user already wrote.

## Where the list comes from

- **The source is the Data Stash index of the conversation's session:** `listDocuments(sessionId)` (`packages/harness-patterns/stash/document-store.server.ts:459-488`) returns each non-expired document's metadata: `filename`, `mimeType`, `size`, `uploadedAt`, `hidden`, `archived`, `ingestStatus`, `provenance`, `converted` (`:43-97`). The retriever's own backend already calls it once per session (`stash/document-ingest.server.ts:392`).
- **It must be read once per run, before iteration 1, not per iteration and not at construction.** The state builder is a synchronous function called every iteration (`decisionLoop.server.ts:176, 454`), so it cannot fetch. And patterns are built once per conversation and cached for its life (`app/src/lib/harness-client/session.server.ts:95-98`), while the document set changes with every upload. The package already has the right precedent: a per-run resolver the host injects, like `tenantId: () => getRequestUserId()` (`session.server.ts:118`). _Proposed:_ an optional `AgentDeps` function beside `createRedisBackend` and `pseudonymiseForWeb`, and an optional `documents` source on `decisionLoop`'s config; `DecisionLoopStateInput` gains the resolved value.
- **Hidden and archived documents are left out.** The store defines them as "hidden from LLM context" (`document-store.server.ts:59-62`), and sandbox hydration skips them (`packages/sandbox/work-artifacts.server.ts:100`). This note keeps hidden files off the list.
- **Cost, which is the real objection to "just list them every turn".** `listDocuments` is one `smembers` plus one `json_get` per document, serial through the gateway, and each `json_get` returns the document's **whole content** (`getDocument`, `:387-401`; content is up to 5 MiB per file, `:162`) only for `stripContent` to discard it. The source comment puts it at ~1.6 s per call (`:435-441`); that figure is a comment, not re-measured here. The result is cached for 30 s, but the cache is dropped on every store, flag change and delete (`:364, 563, 595`), which is exactly the turn that follows an upload, the turn this feature exists for. A conversation with no documents still pays the `smembers`. Before building, a builder must measure the real cost, and almost certainly add a metadata-only read (a `json_get` of the metadata paths) rather than call `listDocuments` as it stands.
- **A count from the index alone is an upper bound.** The index set outlives expired document keys until `listDocuments` prunes them (`:474-481`), so an index-only count can name documents that no longer exist. The count and the names should come from the same read.
- **I found no cap on documents per session** (upload route and service: only a per-file size limit). The list needs its own bound.

## What the state would look like (proposed)

Placed after the conversation window and before **This turn so far**, so it is constant within a turn and keeps the state append-only. When the conversation has no visible documents the block is omitted, so such a state is byte-identical to today's.

```
Conversation (recent turns):
User: Compare the Project count in the knowledge graph with the target count in lantern-notes.md. …

Uploaded documents in this conversation:
- "lantern-notes.md" (Markdown, 1.2 KB, searchable), named by the user
- 1 other document (name not shown)

This turn so far:
(nothing yet)
```

- **Tier floor:** `Uploaded documents in this conversation: 2 (names not shown)`.
- **Unreadable list:** `Uploaded documents in this conversation: unknown (could not be read)`, never "none", plus one recorded `warning`.
- **The matching rule.** A name is revealed only if it appears in a **user line of the state's own conversation window** (the lines `conversationTurns` produces, `typedDecision.server.ts:403-416`). That is the invariant that makes option 4 disclose nothing new. The test is the exact file name, or its stem when the stem is at least five characters, as a whole token, case-folded and NFKC-normalised. Two documents with the same name show once (hydration already prefers the newer, `work-artifacts.server.ts:94-96`).
- **Type** is mapped from `mimeType` through a fixed allowlist (Markdown, text, CSV, PDF, Word, Excel, image, other), never printed raw: `mimeType` is the browser's string, stored as sent (`app/src/lib/stash/upload-service.server.ts:112`).
- **Searchable** is derived from `ingestStatus`: `indexed` reads "searchable", anything else "not searchable". This tells the decider that a CSV is for code (`office-data`) and a notes file is for search, from metadata alone.
- **Bounds (proposed, to be measured, not derived):** at most 10 names, 80 code points each (cut before sanitising), the block capped at 1,000 characters, then "(+K more)". Order: newest first, ties broken by document id, because `listDocuments` sorts on `uploadedAt` alone (`:485`) and the index set's own order is unspecified.
- **Size on the wire is not the constraint.** Run 3's first decision was 324 input tokens against a 32k state window (`jev-decide.server.ts:530-531`); the bounds exist for abuse and determinism, not for fit.
- **The heading and wording are tunable** and should use the route criterion's own words ("uploaded", "documents in this conversation"). Treat any wording as a hypothesis for the live pass, as #697 did.

## Threat model

**Assets.** (1) File names as user data; (2) the routing integrity of the decider; (3) the structure of the state string; (4) other users' documents; (5) the tier boundary: private-tier content must not reach a public provider; (6) what is persisted and logged.

**Who controls a name.** Not only the user. A stash document's name comes from: a browser upload (the user, or a file the user obtained elsewhere), stored verbatim from `blob.name` or the JSON body with no length cap or character filter (`upload-service.server.ts:109, 138`); a file copied from Microsoft 365 (`graph-file`, P4), whose name a third party chose; a promoted sandbox output (`sandbox-output`), named by the agent inside the box; a triggered run's recording, named by whoever called the trigger (`app/src/lib/harness-client/action-runner.server.ts:17-19`). **Treat every name as untrusted text, whatever its provenance.**

What a successful name-borne injection can do is bounded: the decider answers one `choice` over at most five labels and calls no tool. It can steer a route, waste iterations (up to `maxIterations`, 6) or end early with `answer`. It cannot reach a child's prompt unless the name is carried there (T5).

**Failure policy, stated.** A failed list read is **fail-open on the routing aid, fail-closed on disclosure**. If the read throws or times out, the state carries the explicit "unknown" line (never "none", which would read as a claim), one `warning` is recorded, and the turn runs as it does today. If the owner scoping, the tier line or the release filter cannot be evaluated, the names are omitted and only the count is shown, or the block says "unknown". A silent "no documents" is the one outcome not allowed.

## Cache, determinism, resume

- **Caching.** No provider cache sits on the decide path (the transport records no cache reads, and the provider documents none; see [the state section](decision-loop-agent.md#what-the-decisions-model-sees-each-iteration)), so changing the state costs no cache. The block is constant within a turn and sits ahead of the iteration lines, so the append-only property holds. It changes between turns only when the set of documents or the user's lines change.
- **Determinism for the suites.** The ordering above makes the string byte-identical for the same inputs, and a conversation with no documents is unchanged, so scenarios 01-03 are untouched by construction. The eval driver seeds its documents from a map (`app/evals/general-next/driver.ts:175-176`), so scripted runs are reproducible.
- **Resume (slice 6).** The list is an input to a decision, not run state. A resume makes no decide call for the paused iteration, and later iterations read the list once on re-entry, so a file added while the person was deciding is seen from then on. Nothing about the list needs rebuilding from events. The release gate (slice 9) runs before the orchestrator on a flipped turn, so on the Anthropic tier the list is built after the person's answer and sees released versions only. An unattended run that the gate stops never builds it.

## Questions for the owner

Each has a recommended default; none is a prerequisite for the next.

- **Q1. Which option?** Recommended: option 4 on the private tier, count only elsewhere. Blocks: scenario 13, hence the flip gate's must-set.
- **Q2. May the Anthropic tier's decisions host receive uploaded-file names?** Recommended: not now. It is a different processor from the model provider (SD-12), and the Anthropic tier's decider is unmeasured on this agent.
- **Q3. Is showing every name (option 1) ever wanted on the private tier?** Recommended: not in v1. Widen on a live result that shows option 4 is not enough; it is one function and a mode.
