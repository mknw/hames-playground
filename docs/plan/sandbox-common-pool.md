# Common-pool sandbox VM mode (Design note)

> **Status: Not built; no build until the owner reads this.** Design only, for [#648](https://github.com/mknw/hames-playground/issues/648) Q6 as the owner answered it ([comment 6269961143](https://github.com/mknw/hames-playground/issues/648#issuecomment-6269961143)): per-environment VMs, plus a **common-pool** mode with one VM for both environments and a broker inside it, chosen by a setting. Q3 (gVisor) is still open and appears here only as options. Nothing was run against Docker, Incus or any host. Every `file:line` refers to `main` at `a167d530`. SD-19, SD-20 and SD-21 apply. The posture described below comes from the source, not from the brief, which is stale on these points ([#648 §6 finding 2](https://github.com/mknw/hames-playground/issues/648)).

## The decision in one paragraph

The setting is `SANDBOX_VM_MODE`, with the values `per-env` (the default) and `common-pool`. It belongs to the operator-side provisioner in `@hames-ai/sandbox`. The app never reads it.

- **`per-env`** is what `createIncusEnvironment` builds today: one restricted Incus project and one VM per environment. The VM's dockerd listens on TLS, and the app holds root inside its own environment's VM.
- **`common-pool`** builds one project and one VM for both environments. dockerd inside that VM listens only on a unix socket, and only the broker can reach it. The broker is a small Go service, built from a pinned, reviewed commit. It terminates one mTLS client identity per environment and accepts only the six operations from #648 §1. Each environment's labels, name prefix, quotas and image allowlist come from that identity.

The app's code path does not change in either mode: the same four `SANDBOX_DOCKER_*` settings point either at a VM's dockerd or at the broker. Its permitted operations do change ([§4.1](#41-app-side-no-code-change)). The cost of common-pool is stated plainly in [§2](#blast-radius-stated-plainly): **a broker bug, or root inside the shared VM, crosses environments.** Per-env has no such crossing, because a VM boundary separates the environments.

### Blast radius, stated plainly

- **Per-env.** A compromised app, or code escaping a box, gets root in **that environment's VM**. That reaches only that environment's boxes, whose data the app can already read through its own stash. The other environment sits behind a VM boundary.
- **Common-pool.** A compromised app gets only what the broker allows. That is less than per-env grants, **provided the broker is correct**. But two failures cross environments:
  1. **A broker bug.** A field the rebuild lets through, an ownership check that is skipped, or an exec id that is not bound to its creator would let dev act on release boxes, or start a container that is root in the shared VM.
  2. **Root in the shared VM.** A runc escape from any box lands next to both environments' boxes, their `/work` tmpfs contents (including stash documents hydrated into `/work/in`), their live exec streams, dockerd and the broker's server key and binary. The client keys stay with the operator and the apps; the VM never holds them (`incus-environment.server.ts:475-489` sends the guest only the CA, the server leaf and its key).
     - **Exfiltration.** The guest network is seeded with a default route (`incus-environment.server.ts:643-651`), and the package does not establish firewall isolation from host services or other bridges (README `:357-359`). What leaves the VM after an escape is whatever the operator's bridge rules allow. Common-pool therefore requires a default-deny egress rule on the pool bridge, proven as operator evidence (§4.3).
     - **Audit.** The broker's audit lines (§3.7) are written inside the same VM, so root there can erase them. In v1 they are not evidence after a VM-root compromise (CP6).
- **Availability is coupled too.** One VM, one dockerd and one broker serve both environments, so an outage or a maintenance cutover stops both (CP5). Per-env takes one environment down at a time.
- So common-pool trades a VM boundary between environments for a narrower per-app capability, plus one VM's overhead saved. That saving is unmeasured: the only figure is a bare-metal forum report cited in #648 comment F. **Choose common-pool only where a dev compromise reaching release boxes is acceptable, or once gVisor is forced (§7).**

## 3. Broker contract

v1 accepts exactly #648 §1 rows 1-6. Rows 7-9 (networks, egress proxy, cache volume) are refused, because every sandbox route pins `egress: 'mcp-only'` (`packages/agents/agents/sandbox.server.ts:200,213,221`; `general-next.server.ts:106`). ### 3.2 Create: rebuild, not filter

The broker decodes the create request into a typed struct with **unknown fields refused at any depth**. It then builds a fresh body from that struct and sends only the fresh body. It never forwards the client's bytes.

**Unknown is not the same as forbidden.** The Docker CLI marshals whole `Config` and `HostConfig` structs, so a real `docker run` also sends zero values such as `Privileged: false`, `Binds: null`, `CapAdd: null`, `Env: null` and `User: ""` (from the upstream types, which carry no `omitempty`; P20's recording is what will confirm it). The rule has three parts:

1. The struct models every field the pinned API version's CLI sends.
2. A forbidden field is accepted at its zero value and refused at any other value.
3. A field outside the struct is refused.

Part 3 alone cannot catch a case variant such as `HostConfig.PRIVILEGED`: it decodes into the known `Privileged` field, so part 2 is what refuses it. P10a and P10b pin the two parts separately.

**Write it in Go.** dockerd decodes with Go `encoding/json`, which matches field names case-insensitively, so a check written in another language can read `hostconfig.privileged` differently from the daemon (#648 §3). With the same decoder on both sides, that mismatch cannot arise.

### 3.3 Identity, labels, names and ownership

- **Identity comes only from the certificate.** The certificate must chain to the pool CA, **and** its SHA-256 fingerprint must appear in the broker's identity map. The map value is the environment. The broker does not use the CN, any header or any label as the identity.
- **The environment label is forced.** If the client's `kg-sandbox-environment` label, or its list filter, names a different environment, the request is **refused, not rewritten**. An app whose `SANDBOX_ENVIRONMENT` disagrees with its certificate is therefore refused at its first box create, instead of running under a label it does not know about (`docker-backend.server.ts:458-465`). That is not necessarily at startup: on a lazy route the first create happens during a user turn (`general-next.server.ts:109`), and the startup reaper's refused `ps` is swallowed (`docker-backend.server.ts:553-555`). The operator smoke step in §5 catches it before traffic does.
- **The name prefix** stops one environment squatting another's names, which would block the other's boots with name conflicts. The app is unaffected: it addresses boxes by the id that `run` returns (`:474`) and reuses the client name on reset (`:616`).
- **Ownership check** on start, exec, inspect and delete: the broker first inspects the target over the unix socket. It requires `kg-sandbox=1`, the identity's environment label and the identity's name prefix. On any mismatch it answers **404**, sends nothing on to dockerd, and does not confirm that the box exists. When the check passes, the broker forwards the **full container ID the inspect resolved**, never the client's string. A name or an ID prefix is resolved again at use, so a box renamed or recreated between the check and the use could otherwise be a different box.
- **List.** The broker discards the client's filters and applies `label=kg-sandbox=1` and `label=kg-sandbox-environment=<identity>` itself. This turns the reaper's environment label into a boundary, where today it only prevents accidental cleanup (README `:384-385`; `docs/PREVIEW.md:1313-1314`).

### 3.4 Exec and upgraded streams

- **Exec create.** The ownership check runs first. Then the broker rebuilds the body: `AttachStdin/Stdout/Stderr`, `Tty` and `Cmd` only, with `Privileged: false` and **no `User`**, so the exec runs as the image's `USER sandbox` (`rootfs/Dockerfile:103`). The §3.2 rule applies to exec create and exec start bodies too, since the CLI always sends `Privileged: false` and `Env: null`. `Privileged`, `User`, `Env` and `WorkingDir` are accepted at their zero values and refused at any other value. `Cmd` is not allowlisted, because the box runs arbitrary agent code by design. What exec must not do is escape the image user.
- **Exec ids are daemon-global.** The broker records exec id → identity at create, and refuses start, resize or inspect of an exec id it did not record for that identity (404). After a broker restart the map is empty, so an exec stream that was in flight must be re-opened.
- **Restarts and the app.** After a broker restart, a surviving box has a dead `docker exec -i` child. The app does not notice: `AttachmentTable.acquire` checks only the box's health and reuses the attachment (`attachment-table.server.ts:113-129`). Transports are re-opened only when a new attachment is built (`:154`), so the session stays wedged until idle eviction (`idleEvictMs`, 1 h, `settings.ts:66`). A **dockerd restart inside the VM** has the same effect on streams, and more: exec ids are daemon-global and are lost, and `--rm` boxes die with dockerd (no live-restore), so they read as `gone` and boot again. The quota counts re-derive from dockerd's state, so they do not drift. This already happens on any network break to a per-env VM, so it is a pre-existing gap and not one this design adds. The pool path re-opens per run and is unaffected (`with-sandbox.server.ts:655-681`). The fix belongs in a follow-up issue, "evict an attachment whose transport closed", not in the broker.
- **Upgraded connections.** `exec start` is answered with `101`, and the broker then proxies the hijacked raw stream in both directions. It honours half-close (`CloseWrite`), so stdin EOF reaches the box, and it tears the stream down when either side closes or the box is deleted. Resize is an ordinary POST.

### 3.5 Per-environment quotas

The broker holds four ceilings per identity: **live box count, Σ `Memory`, Σ `NanoCpus`, Σ `PidsLimit`**. It also holds per-box ceilings for the fields in §3.2. tmpfs pages are charged to the container's memory cgroup, so `Memory` also bounds `/work`.

- **Counting.** Usage is counted from dockerd's own state (a label-filtered list) under a per-identity lock at each create. A broker restart therefore cannot reset the counts, and concurrent creates cannot overshoot.
- **Refusals.** A create over quota is **refused**, not queued. The app sees `SandboxBootError` (`docker-backend.server.ts:710-717`). The quota must therefore cover the app's own bounds. In-flight boxes are capped at `globalCap` 16 (`settings.ts:56`). Parked attachments are capped separately at `maxAttachments` 8 (`settings.ts:61`) and hold no scheduler slot (`attachment-table.server.ts:213-216`). The pool's parked boxes are capped at the sum of the `warmPool` caps, 4 (`settings.ts:62`). The Shell path acquires without the scheduler (`pty-manager.server.ts:144`). No single app-side number bounds the live boxes, so the broker quota is the only hard per-environment count.
- **Starvation of box CPU and memory.** Dev cannot starve release of box CPU or memory, because the partition is static: at load, the broker refuses any configuration in which Σ of the environment quotas plus a fixed reserve for dockerd and the broker exceeds the VM's CPU and memory. Whether to allow bursting instead is open question CP2.
- **The shared control plane and disk.** Box quotas alone leave these open. Each box opens two `exec -i` streams (`docker-backend.server.ts:304-317`), and create/rm churn is not bounded by a live-box count. So the static partition also carries, per identity: a ceiling on open connections and on hijacked streams, a request-rate limit, a maximum request body size, and handshake and idle timeouts. It also carries a disk budget for the VM's writable layers, and `LogConfig: none` (§3.2) removes the unbounded log path. The load-time check (P7) covers these ceilings as well as CPU and memory.

### 3.6 Refused

Everything not listed in §3.1 is refused with 403, or with 404 for object lookups, and nothing reaches dockerd. That includes:

- `/images/*` (pull, build, load, tag, inspect, remove) and `/build`. When an image is missing, `docker run` pulls it, so that request is refused too.
- `/containers/{id}/archive` (cp), `/commit`, `/attach`, `/logs`, `/export`, `/top`, `/stats`, `/changes`, `/events`.
- `/containers/{id}/update`, which would lift memory and pids limits after create.
- `/rename`, `/pause`, `/kill`, `/restart`, `/stop`, and every `/prune`. The reaper's `network prune` (`:571-581`) is refused, which is harmless: its failure is swallowed (`:591`).
- `/networks/*`, `/volumes/*`, `/info`, `/system/*`, `/auth`, swarm, plugins, secrets, configs and session.
- A generic `inspect` falls back to image and network lookups for a missing id. The broker answers those with 404, which `health()` already reads as `gone` (`:602-605`).

### 3.7 Failure policy

**Fail closed everywhere, with no silent clamping.** When the broker is down, every sandbox operation fails; the connection never retries against another endpoint (README `:209-210`). Unknown fields, out-of-ceiling values, an environment mismatch, a refused route or an exceeded quota each produce a named error and an audit line (identity, route, reason, and never a body). The audit lines live inside the VM, so after a VM-root compromise they are not evidence (CP6). A value is never quietly lowered to fit. A box that runs with a weaker posture than the app asked for is the silent degradation SD-19 warns about.

### 3.8 Build and provenance

- **Source.** The broker source goes in `packages/sandbox/broker/`, a Go module. It stays outside the npm tarball, which ships only `*.ts` (`packages/sandbox/package.json` `files`), the same way `packages/sandbox/scripts/vm-image/` does.
- **Pinning.** The binary is built from a pinned, reviewed commit and enters the VM image as a hashed input in the image lock, next to the flavours (`packages/sandbox/scripts/vm-image/README.md`, "Local lock schema"). The Incus image fingerprint therefore covers it. It is **never built from the dev checkout**.
- **Which image carries it.** Only a pool image. The per-env image stays as it is and never contains the broker. Today `build.py` requires `schema == 1` (`packages/sandbox/scripts/vm-image/build.py:69`) and exactly three flavours (`:88`). The lock therefore moves to `schema: 2`, which adds an image kind. A pool lock must name the broker, and a per-env lock must not. A schema-1 lock still builds today's per-env image unchanged. Making the broker a required input of every lock would break every existing per-env build.
- **Where the policy lives.** The parts fixed at image-build time are baked into the image: the binary, its systemd unit, and each tag's config ID. The lock carries `base`, `data` and `office`, but not `image-processing`, so that tag is out of the v1 allowlist. Adding it to the lock is a prerequisite for allowing it. The per-provisioning parts arrive by cloud-init, as `daemon.json` does today (`incus-environment.server.ts:475-523`): the listen address, the TLS material, the identity map and the quotas. Changing any of them on a live VM is drift and needs a cutover (§2, CP5).

## 4. How the existing code reaches it

### 4.1 App side: no code change

- **The trap.** The MCP SDK passes the exec child only an allowlisted environment, so `DOCKER_HOST` never reached row 4 (#648 §1).
- **How #651 solved it.** The fix used argv flags, **not a Docker context**:
  - `dockerConnectionFromEnv` turns the four `SANDBOX_DOCKER_*` settings into `--host`, `--tlsverify` and the three file flags (`docker-connection.server.ts:16-71`).
  - `dockerInvocation` prepends those flags to every child's argv, and strips `DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_TLS`, `DOCKER_TLS_VERIFY` and `DOCKER_CERT_PATH` from the child's environment (`:74-94`). The MCP streams keep the SDK allowlist (`docker-backend.server.ts:317`), and the flags travel in argv.
  - The backend captures the connection once (`:444-447`), and the PTY reuses the handle's copy (`pty-manager.server.ts:158-166`).
- **Common-pool** is therefore four values: the broker address and this environment's CA, client certificate and key. A restart applies them (README `:215-217`).
- **What becomes a refusal in common-pool.** The broker owns these, so a non-default value now fails loudly, where per-env would accept it: `SANDBOX_SECCOMP_PROFILE` and `SANDBOX_APPARMOR_PROFILE`, any `SANDBOX_PIDS_LIMIT` or `SANDBOX_WORK_TMPFS_MB` above the ceiling, a `SANDBOX_IMAGE` outside the allowlist, the `image-processing` rootfs, and a `SANDBOX_ENVIRONMENT` that differs from the certificate's identity. Two capabilities that run in a per-env VM are also refused: any egress profile other than `mcp-only` (it needs `/networks/*`, #648 §1 rows 7-8), and the per-tenant cache volume (row 9, `/volumes/*`).

### 4.2 Provisioner: what changes in `incus-environment.server.ts`

**Changes**, all behind `mode: 'common-pool'`:

- **Options.** The options become a discriminated union. Common-pool takes `environments: [{ name, quota: { boxes, memoryMiB, cpu, pids } }]` (at least two distinct slugs, `pool` refused) in place of the single `environment`. The project name becomes `sandbox-pool`. `binding` (`:201-209`) gains `mode` and the environment list, so a state directory written by one mode is refused by the other.
- **Credentials.** `credentials()` (`:334-407`) issues one client leaf per environment in place of the single `client` role at `:372`.
- **Cloud-init.** `cloudConfig()` (`:475-523`) writes `daemon.json` with `hosts: ["unix:///run/docker.sock"]` and no TLS keys. It adds the broker's configuration and enables its unit. The Docker server leaf becomes the broker's.
- **Return value.** `reconcile()` returns `connections: Record<env, dockerEnv>`. Each entry is validated through `dockerConnectionFromEnv`, as at `:684`, and each names only its own key. Per-env keeps its `dockerEnv`, so existing callers are unchanged.
- **Teardown.** Teardown removes every client leaf. Its file sweep (`:727-728`) already matches them.
- **Package surface.** The build PR updates the package's own docs and release metadata for the new operator option: the README's provisioner section (`packages/sandbox/README.md:234`), `SPEC.md:79` and `GUIDE.md:62`, a minor changeset for `@hames-ai/sandbox`, and `scripts/pack-smoke.sh` (`.github/workflows/ci.yml:416`).

**Stays as it is:**

- every project restriction (`:409-440`) and the ownership checks (`:441-474`);
- the bridge and address checks (`:528-546`), NIC MAC/IP filtering (`:590-601`) and seeding by MAC (`:636-670`);
- the operation journal (`:225-292`), `exclusive` (`:213-224`), the image-server and port checks (`:176-189`), and the teardown order (`:687-730`);
- `limits.virtual-machines: 1`. The manager and project certificates never reach an app (README `:307-311`).

### 4.3 Compose and the clone validator

These apply to **both** modes before either can reach the two-clone deployment.

- **The current overlay is single-app.** `docker-compose.sandbox-vm.yaml` defines only `app` (`:4-15`).
- **The validator refuses it.** The clone validator refuses any bind other than `/configs` and the socket (`scripts/validate-clones.mjs:28-36`), and therefore refuses that overlay's three TLS file binds. Checked against a synthetic config: it throws `No checkout or runtime env bind mounts`.

The proposal is one clones-aware overlay. It sets the four settings for both `app` and `app-dev`. It declares the mode **per app**, the same way `x-clone-dev-docker-socket` is declared (`docker-compose.clones.yaml:15`):

```yaml
x-sandbox-vm-mode:
  release: socket # socket | per-env | common-pool; default socket
  dev: per-env # per-env | common-pool
```

The validator reads that declaration and nothing in the app does. One top-level value could not express the interim the owner set in Q2 (comment 6269961143): the release app keeps its host socket until its own VM lands, while dev moves to a VM. The validator already models the socket policy per app (`scripts/validate-clones.mjs:59-70`). An app declared `per-env` or `common-pool` has no `/var/run/docker.sock` mount and exactly the three read-only TLS binds. `socket` keeps today's rule. Under per-env, release can move on its own. Under common-pool, the pool provisions both identities, and release moves when its declaration changes.

**Operator evidence that common-pool requires.** A default-deny egress rule on the pool bridge, proven separately, as the README already asks for any guest (`:357-359`). Without it, an escape from a box reaches whatever the bridge routes to (§2).

**Scope.** This section covers only the clones path. The single-host deployment keeps the release app's host socket (`docker-compose.yaml:361-366`), per the owner's Q2 answer.

## 5. Switching modes

A mode switch is a cutover, not a live migration. Box state is tmpfs, and the attachment table, pool and scheduler are per-process singletons (`with-sandbox.server.ts:217-221`).

1. **Provision the target topology alongside the current one.** The project names differ (`sandbox-<env>` against `sandbox-pool`), so both can exist together. The host needs capacity for both.
2. **Drain sandbox turns, then repoint and restart each app.** Its four settings change. Durable files live in the stash (`settings.ts:63-65`), so only an in-flight turn's unpromoted `/work/out` is lost, as with any restart.
3. **The reaper runs once per process, against the new endpoint** (`with-sandbox.server.ts:223-258`). It never sees boxes left in the old VM. Those go when the old topology is torn down: `teardown()` deletes the VM (`incus-environment.server.ts:699-711`).
4. **Credentials do not carry over.** A per-env leaf chains to its own environment's CA, which is neither the pool CA nor in the identity map, so the broker refuses it. Old leaves stop meaning anything once their dockerd is gone. Teardown deletes their files. The same applies later within common-pool: a rotation, a quota or identity-map change, or a broker upgrade is this same cutover, for both environments at once (§2, CP5).
5. **Smoke each identity before traffic.** After provisioning, list boxes with each environment's certificate: its own environment label answers 200, and the other environment's label answers 403. This catches a certificate or `SANDBOX_ENVIRONMENT` mismatch that the app would otherwise meet only at its first box create (§3.3).
6. **Labels are unchanged** (`kg-sandbox-environment=<env>`). The warm pool starts empty in the new process and refills by parking released boxes. `prewarm` has no production caller. In common-pool, parked boxes count against that environment's quota (§3.5).
7. **The reverse switch (common-pool → per-env)** is the same procedure. A transient mixed state, with one environment per-env and the other in the pool, works technically, and the per-app `x-sandbox-vm-mode` (§4.3) can describe it truthfully. Leaving that state for long would mean operating both topologies, so this note does not recommend it beyond the cutover.

## 8. Open owner questions

**CP1. Must gVisor be in place before common-pool carries release traffic?**

- **Plain words.** In common-pool, the only thing between a box escape and the other environment's boxes is the container runtime. gVisor would add a second layer there.
- **Implication.** Without it, a runc escape from a dev box reaches release boxes: their `/work` contents, including hydrated stash documents, and their live streams. What leaves the VM from there is whatever the pool bridge's egress rules allow, and the broker's audit trail in the same VM can be erased (§2). With it, common-pool waits on the Q3 spike.
- **Options.** (a) Require runsc, forced by the broker, for common-pool. (b) Allow runc now and add gVisor later. (c) Common-pool carries release only after Q3 is settled. Until then the release app is declared `socket` or `per-env` (§4.3), which the operator sets in the compose declaration. The mode is per deployment, so it cannot be limited to a class of traffic.
- **Recommendation.** (c) now, then (a) if the Q3 spike passes.
- **What it blocks.** Whether broker v1 forces `Runtime`, and when common-pool may carry release.

**CP2. Quotas: a fixed share each, or a shared pool with a guaranteed minimum?**

- **Plain words.** Either each environment gets a hard slice of the VM, or dev may borrow release's idle capacity.
- **Implication.** Fixed slices cannot starve release, but leave capacity idle. Borrowing needs pre-emption or reservation logic in privileged code.
- **Options.** (a) A static partition. (b) A reserved minimum for release, with dev bursting above it.
- **Recommendation.** (a) for v1.
- **What it blocks.** The broker's quota code (§3.5).

**CP3. Is a Go broker, with a Go toolchain in CI and the image pipeline, acceptable?**

- **Plain words.** The broker should be written in the same language as Docker's own request decoder. That adds Go to the repo.
- **Implication.** It needs a pinned Go toolchain in CI and in the broker build, plus a reviewed binary per release. A TypeScript broker would have to reproduce Go's case-insensitive decoding exactly, which is the class of bug the rebuild exists to remove.
- **Options.** (a) Go. (b) TypeScript in the package.
- **Recommendation.** (a).
- **What it blocks.** Any broker code.

**CP4. Should per-env also put the broker in front of each VM's dockerd?**

- **Plain words.** The same broker could run inside each environment's VM. Each app would then hold only the six operations, instead of root in its VM.
- **Implication.** It narrows per-env further at no new code cost once the broker exists. It also adds the broker's failure modes to per-env, which today has none.
- **Options.** (a) Not now: two values, as ruled. (b) Later, as an option on `per-env`, after the broker has been reviewed in common-pool.
- **Recommendation.** (a).
- **What it blocks.** Nothing in v1.

**CP5. Is a both-environment cutover acceptable for common-pool maintenance in v1?**

- **Plain words.** In common-pool, rotating or revoking a certificate, changing a quota or the identity map, or upgrading the broker means rebuilding the one VM both environments use. Both are down for that cutover.
- **Implication.** The policy arrives by `cloud-init.user-data`, and the provisioner refuses any config change on a live VM as drift (§2). Per-env does this one environment at a time, with dev as the canary. Avoiding the joint cutover needs a policy file the broker re-reads, kept outside `cloud-init.user-data` so it is not drift. That is new privileged reload code.
- **Options.** (a) Accept the joint cutover in v1. Use per-env as the canary path: upgrade a dev per-env VM first. No live reload. (b) Add a broker-read policy file with live reload in v1.
- **Recommendation.** (a).
- **What it blocks.** Whether broker v1 has a reload path, and the maintenance runbook.

**CP6. Must the broker's audit lines leave the VM in v1?**

- **Plain words.** The broker logs every refusal inside the shared VM. Root in that VM can erase those logs.
- **Implication.** Kept in the VM, the audit trail is useful for debugging but is not evidence after a VM-root compromise, which is the case that matters most. Forwarding the lines off the VM needs a collector outside it and a transport the guest can reach, which the default-deny egress rule (§4.3) must then allow.
- **Options.** (a) v1 keeps the lines in the VM, and this note says plainly that they are not evidence after a VM-root compromise. (b) v1 forwards them off the VM.
- **Recommendation.** (a) for v1, and (b) before common-pool carries release (CP1).
- **What it blocks.** The broker's logging sink, and the egress rule's allowlist.
