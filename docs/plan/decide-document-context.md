# What the Decide step is told about the conversation's documents (Design note)

> **Status: decided design, not built.** The owner's rulings are recorded under [Owner rulings](#owner-rulings). Nothing here is dispatched, and every identifier marked _proposed_ does not exist. Source claims were read on `origin/main` at `ff1c3a04` (line numbers are that tree's); evidence is from [Eval run 3](https://github.com/mknw/hames-playground/issues/507#issuecomment-6281039851) (synthetic fixtures, private tier, one pass). It extends [`decision-loop-agent.md`](decision-loop-agent.md), which says what the decisions model sees ([What the decisions model sees each iteration](decision-loop-agent.md#what-the-decisions-model-sees-each-iteration)) and says nothing about documents. A security/privacy review is owed before any slice is dispatched; the [threat model](#threat-model) is written for that reader.

## The decision, in one paragraph

Today the decisions model choosing the next route is never told that a conversation holds uploaded documents, so a question that names an uploaded file by its bare name can be routed to the web instead of `read-documents`. **Decided: tell it, and let the tier set how much.** On the private tier (the run frame's tier is exactly `'verda'`) the state lists **every visible document's name, type and size** in a capped list: at most 10 names, then a count of the rest. On every other tier, including an unrecognised tier and a frame with no tier slot, the state carries **a count only**. **The invariant: no uploaded-file name is ever sent to the Anthropic tier's decisions host.** Hidden and archived documents stay off the list and out of the count. The change is **unmeasured**: the decider is a small classifier, one live sample is all there is, so a [replay probe](#slices) (slice 0) gates the build and a live pass (slice 11) gates keeping it (see [Tests](#tests-and-mutations-a-builder-needs)). Scenario 13 is in the flip gate's must-set (run 3: fails 11 and 13), so until 13 passes the gate cannot be eligible.

## The problem and the evidence

The decide request is `{ model, state, questions }` (`packages/harness-baml/jev-decide.server.ts:299-305`). The state is built per iteration by `renderState` from three things only: the conversation window, one line per finished step this turn, and the last N route outputs in full (`packages/harness-patterns/patterns/decisionLoop.server.ts:361-386`, called at `:454`). The questions carry each route's description. No document list is part of either.

Run 3, scenario 13 (`two-sources`: "Compare the Project count in the knowledge graph with the target count in lantern-notes.md. How far apart are they? Cite the notes."). The conversation had `lantern-notes.md` and `lantern-sales.csv` in its stash. From the run's capture file (gitignored, synthetic):

| Decision | State the decider was given                                                                                                                     | Its distribution                                                                             | Choice           |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ---------------- |
| 1        | the user line, then `This turn so far: (nothing yet)` (324 input tokens, 144 ms)                                                                | info-retrieval 0.633, think 0.233, answer 0.086, **read-documents 0.025**, office-data 0.025 | `info-retrieval` |
| 2        | the same user line; `1. info-retrieval — succeeded`; its result: the graph has 42 projects and "lantern-notes.md" holds one line with no target | answer 0.743, **read-documents 0.166**, info-retrieval 0.066, think 0.013, office-data 0.013 | `answer`         |

What this shows:

- **Nothing in either state says the file is a conversation upload.** `lantern-notes.md` is a bare name that looks equally like a web resource, and the info route treated it as one: it web-fetched the name, got a one-line fixture page, concluded there was no target and answered with 42 only. Run 3 grades that a fail (answer lacks 50 and 8, no citation, `read-documents` never chosen).
- **The wording lever has already been pulled.** The route criteria in the capture are byte-identical in both decisions and already carry #697's text ("an uploaded file the user names without saying "uploaded" … also when an earlier knowledge-graph or web lookup did not find it"; `info-retrieval` says it cannot open uploaded files) (`packages/agents/agents/general-next.server.ts:215-229`). It did not move the distribution. That was #697's own stated risk: a wording hypothesis, unmeasured until run 3.
- **The passing neighbour differs by one word.** Scenario 12's message says "the **uploaded** lantern-notes.md … cite the **document**"; the #697 replay found that to be the one word the old `read-documents` criterion could match. A state line that says which files are uploaded supplies the same signal without relying on how the user phrased the question.
- **Scenarios that name uploaded files:** 09, 10, 12, 13, 14, 17 (and 15/16 once P4 ungates them). Only 13 fails on this axis in run 3; 09 and 10 did not run (stop threshold), so the effect on them is unknown.

What the evidence cannot show: one sample per decision; the decider is a 4B classifier reached through a self-hosted shim, and the Anthropic tier's decider (`JevDecide`, `packages/harness-baml/clients.server.ts:406`) has never been measured on this agent. It is not evidence that a state line would flip scenario 13. It is evidence that, as built, the decider cannot know.

## Options considered

"Disclosure" is what the decisions endpoint receives that it does not receive today.

| #   | What the decider is shown                                                                     | New disclosure                                     | Fixes the 13 shape?                                                            | Ruling                                                                                                                                                                                                                        |
| --- | --------------------------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | every visible document's name, type, size (capped list)                                       | **all names**, including ones never mentioned      | likely; unmeasured                                                             | **Chosen on the private tier.** The largest disclosure; names can carry identities and instructions (T1, T7), accepted there because the box is the one the conversation already goes to.                                     |
| 2   | a count only: "N documents in this conversation"                                              | the fact that documents exist                      | partly: supplies "uploaded", not _which_ file; unmeasured                      | **Chosen on every other tier.** A count can bias every turn toward `read-documents` (a false-positive direction); the live pass measures it.                                                                                  |
| 3   | nothing (status quo, plus more wording work)                                                  | none                                               | tried, did not move 13                                                         | Not chosen. Each wording round costs a live pass.                                                                                                                                                                             |
| 4   | names a user line in the state already contains, plus a count of the rest (a lexical matcher) | **none**: the matched name is already in the state | likely: ties the user's own word to "this is an uploaded document"; unmeasured | Not chosen. Its one advantage was zero new disclosure; the owner ruled the private tier may disclose every visible name, which also removes the matcher and its miss on a paraphrase ("the notes"), where a count only helps. |

**Alternatives that do not put names in the state:**

- **A. A `files` hint from the UI.** The composer sends the ids of documents it means; the server validates them against the caller's session index and renders them in the same block. Strongest signal (intent, not lexical matching) and no matcher. But the wire has no such field (`app/src/routes/api/events.ts:38-41` takes `sessionId, message, agentId, mode, settings`), the stash is conversation-scoped with no "attached to this message" concept, a browser-supplied id is a new input to validate (SD-13), and triggered or routine runs have no composer. A sensible v2 on top of the decided list, not instead of it, and the only route to naming a file on a tier that gets a count.
- **B. A pre-Decide retrieval probe.** Run one vector search with the user's message before iteration 1 and show the top hit's source. It needs the document count first to skip empty conversations (so it subsumes the count), costs an embedder call and a KNN query on every turn with documents, carries content-derived information (a hit) rather than a name, and with `EMBEDDINGS_PROVIDER=openrouter` would send the user's message off-box on every turn, adding the "embedder" exit that P4's table has to hold. Rejected for v1.
- **C. More description wording.** Cheap to try, costs a live pass to learn anything, and has already failed once. Fine as a complement.
- **D. The info route's own lever (a neighbouring lever, not designed here).** The info loop web-fetched a bare file name because nothing tells its controller that conversation uploads cannot be fetched (#697 recorded this as "a separate lever"). It has value even if Decide routes right, because "graph first" is a legitimate first move for a two-source question.
- **E. Force the route in code when a name matches.** Rejected: it overrides the decider the owner chose (G12), and a named file can legitimately be `office-data` (run code over it) or `info-retrieval` (the user gave a web address).
- **F. A per-run suffix on the `read-documents` description.** The questions carry each route's description and the spec is rebuilt every iteration (`decisionLoop.server.ts:443-447`), so "this conversation holds N uploaded documents" could ride the channel the classifier already scores, with no state change and no matcher. Its disclosure is option 2's (the count) and the same tier rule would apply. **Not the build, but a slice 0 variant.** The owner ruled the state block (names on the private tier, a count elsewhere), and a description cannot carry a capped name list without growing a second, per-route copy of it. It costs nothing to test in the same replay, though: if F moves scenario 13's distribution as far as the block does, it is the cheaper change on the tiers that get a count, and slice 0 reports that.

**Where the line is drawn in code (proposed).** Core never reads the tier, because the tier is an opaque string to it. The host's document source returns what the run may reveal: the visible total always, and a name list only when the run frame's raw tier slot is exactly the private literal. Core renders whatever it is handed. So the policy is one reviewed function in the app's composition root, set in code, never by an environment variable (the same rule as `createWebPseudonymiser({ directory })`).

**The literal is `'verda'`, and the check names it.** The private tier has no value called `'private'` in code: `InferenceTier` is `'verda' | 'anthropic'` (`packages/harness-baml/clients.server.ts:144`), the frame's slot is an opaque string that `activeInferenceTier()` narrows (`:748`), and the decisions transport tests `=== 'verda'` itself (`packages/harness-baml/jev-decide.server.ts:165`). The source compares the frame's raw slot for equality with `'verda'`. Three wrong spellings, each caught by a pin: `!== 'anthropic'` lets an unrecognised value or a typo see names; a comparison with `'private'` is false everywhere, so every run gets a count and the ruling is silently never in force (which is why a positive pin is needed, not only the negative ones); and reading `activeInferenceTier()` instead of the raw slot would hand names to a frameless run on a deployment whose default is `'verda'`, where the safe error is a count. All three have a row in the [unit table](#tests-and-mutations-a-builder-needs).

**Two rules that follow from P4.** (a) A document that P4's slice 5b tags `graph-file`, or marks `privateTier`, and that the person has not released to the Anthropic tier must be absent from the count on any non-private run. The list and the count should be exactly the set `read-documents` could return on that run; on the private run such a document is listed like any other, because `read-documents` can return it there. (b) A name that the user typed is the user's disclosure; a name the user did not type is the app's, and needs the tier line above.

**G14 does not cover names.** The roster covers people in labelled Graph fields and the directory, and wraps the `info-retrieval` route only. A file called "Review - Jane Roe.xlsx" is not in it. On the private tier the name goes to the self-hosted shim as written, with nothing pseudonymised: that is what the ruling accepts. On every other tier no name is sent, so there is nothing to pseudonymise.

## Where the list comes from

- **The source is the Data Stash index of the conversation's session, read strictly:** `listDocumentsStrict(sessionId)` (`packages/harness-patterns/stash/document-store.server.ts:511-527`) returns each non-expired document's metadata: `filename`, `mimeType`, `size`, `uploadedAt`, `hidden`, `archived`, `ingestStatus`, `provenance`, `converted` (`:43-97`). **Not `listDocuments`** (`:474-503`, which the retriever's own backend calls once per session, `stash/document-ingest.server.ts:487`): it returns `[]` when the index read fails (`:484`) and treats any failed per-document read as an expired key and `srem`s the index entry (`:489-497`, because `getDocument` collapses a failure to `null`). Used here, a gateway error would render a silent "no documents", the one outcome the [failure policy](#threat-model) forbids, and would prune live index entries. The strict read throws on any failed read and prunes only after a read that succeeded and returned no document (#599 review F2, `:523`); it is uncached. A metadata-only read (below) must keep both properties.
- **It must be read once per run, before iteration 1, not per iteration and not at construction.** The state builder is a synchronous function called every iteration (`decisionLoop.server.ts:176, 454`), so it cannot fetch. And patterns are built once per conversation and cached for its life (`app/src/lib/harness-client/session.server.ts:94-99`), while the document set changes with every upload. The package already has the right precedent: a per-run resolver the host injects, like `tenantId: () => getRequestUserId()` (`session.server.ts:119`). _Proposed:_ an optional `AgentDeps` function beside `createRedisBackend` and `pseudonymiseForWeb`, and an optional `documents` source on `decisionLoop`'s config; `DecisionLoopStateInput` gains the resolved value.
- **Hidden and archived documents are left out**, of the list and of the count. The store defines them as "hidden from LLM context" (`document-store.server.ts:59-64`), sandbox hydration skips them (`packages/sandbox/work-artifacts.server.ts:100`), and retrieval honours the same flags (#705), so the list and `read-documents` agree.
- **Cost, which is the real objection to "just list them every turn".** The strict read is one `smembers` plus one `json_get` per document, serial through the gateway, and each `json_get` returns the document's **whole content** (`getDocumentStrict`, `:410-437`; content is up to 5 MiB per file, `:163`) only for `stripContent` to discard it. `getDocumentMeta` (`:440-448`) is not metadata-only either: it calls `getDocument`, then strips. The source comment puts it at ~1.6 s per gateway call, **12-21 s for a handful of documents** (`:451-453`); that figure is a comment, not re-measured here, and it is the headline: a per-turn read of that size is not affordable as it stands, and it sets the read timeout in T8. `listDocumentsStrict` is uncached, so it gets no help from the 30 s cache that `listDocuments` has (`:462`), a cache that is itself dropped on every store, flag change and delete (`:365, 578, 610`), i.e. on the turn that follows an upload, the turn this feature exists for. A conversation with no documents still pays the `smembers`. Before building, a builder must measure the real cost and add a strict metadata-only read (a `json_get` of the metadata paths per document, throwing on failure, pruning only on a successful read of no document) rather than call either list function as it stands.
- **A count from the index alone is an upper bound.** The index set outlives expired document keys until a list read prunes them (`:489-497`, `:520-523`), so an index-only count can name documents that no longer exist. The count and the names come from the same read.
- **There is no cap on documents per session** (upload route and service: only a per-file size limit). The list has its own bound, below.

## What the state looks like (decided)

Placed after the conversation window and before **This turn so far**, so it is constant within a turn and keeps the state append-only. When the conversation has no visible documents the block is omitted, so such a state is byte-identical to today's.

**Trim and override.** The block is a fixed section of the default `render` inside `renderState`, so it counts toward `trimToFit`'s budget (the serializer closures re-render the whole state, `decisionLoop.server.ts:381-383`) but is never itself trimmed: what is dropped, oldest first, is conversation lines, then full results, then step lines, and the block is bounded at 1,000 characters. A `config.state` override (`:176`) bypasses `renderState` altogether (`:362`): it receives the host's already-resolved value on `DecisionLoopStateInput`, so off the private tier it holds no names, but it owns its own quoting, cap, sanitising and placement, and none of this section's pins reach it. The rendering is therefore one exported function the default path calls and an override may call; `general-next` passes no override.

Private tier (`'verda'`):

```
Conversation (recent turns):
User: Compare the Project count in the knowledge graph with the target count in lantern-notes.md. …

Uploaded documents in this conversation:
- "lantern-notes.md" (Markdown, 1.2 KB, searchable)
- "lantern-sales.csv" (CSV, 3.4 KB, searchable)

This turn so far:
(nothing yet)
```

- **Every other tier:** `Uploaded documents in this conversation: 2 (names not shown)`, and nothing else about them.
- **Unreadable list:** `Uploaded documents in this conversation: unknown (could not be read)`, never "none", plus one recorded `warning`.
- **Which documents.** Every visible document, with no matching against the user's words. Two documents with the same name show once, the newer, as hydration already does (`work-artifacts.server.ts:94-96`).
- **Type** is mapped from `mimeType` through a fixed allowlist (Markdown, text, CSV, PDF, Word, Excel, image, other), never printed raw: `mimeType` is the browser's string, stored as sent (`app/src/lib/stash/upload-service.server.ts:112`).
- **Searchable** is derived from `ingestStatus`: `indexed` reads "searchable", anything else "not searchable". This tells the decider that a CSV is for code (`office-data`) and a notes file is for search, from metadata alone.
- **The cap (private tier).** At most **10 names**, each cut to **80 code points** before sanitising, and the whole block at most **1,000 characters**: names are dropped from the tail until it fits. **Beyond the cap**, the last line is `- (+K more documents, names not shown)`, where K counts every visible document not shown by name, so the decider still learns that more uploads exist. Order is newest first, ties broken by document id, because the list functions sort on `uploadedAt` alone (`:500`, `:525`) and the index set's own order is unspecified. The newest uploads are the likeliest subject of a question; a named older file beyond the cap is not shown by name and is covered only by the count (the live pass has a scenario for it). The numbers are set values, not measurements.
- **Size on the wire is not the constraint.** Run 3's first decision was 324 input tokens against a 32k state window (the comment above `decideAll.limits` at `jev-decide.server.ts:528-530` and `MODEL_CONTEXT_WINDOWS`, `app/src/lib/settings.ts:151`); the block adds at most 1,000 characters. The bounds exist for abuse and determinism, not for fit.
- **The heading and wording are tunable** and should use the route criterion's own words ("uploaded", "documents in this conversation"). Treat any wording as a hypothesis for the live pass, as #697 did.

## Threat model

**Assets.** (1) File names as user data; (2) the routing integrity of the decider; (3) the structure of the state string; (4) other users' documents; (5) the tier boundary: private-tier content must not reach a public provider, and no file name reaches the Anthropic tier's decisions host; (6) what is persisted and logged.

**Who controls a name.** Not only the user. A stash document's name comes from: a browser upload (the user, or a file the user obtained elsewhere), stored verbatim from `blob.name` or the JSON body with no length cap or character filter (`upload-service.server.ts:109, 138`); a file copied from Microsoft 365 (`graph-file`, P4), whose name a third party chose; a promoted sandbox output (`sandbox-output`), named by the agent inside the box; a triggered run's recording, named by whoever called the trigger (`blob.name`, `app/src/routes/api/agents/[id].ts:86`). **Treat every name as untrusted text, whatever its provenance.**

What a successful name-borne injection can do is bounded: the decider answers one `choice` over at most five labels and calls no tool. It can steer a route, waste iterations (up to `maxIterations`, 6) or end early with `answer`. It cannot reach a child's prompt unless the name is carried there (T5).

**Failure policy, stated.** A failed list read is **fail-open on the routing aid, fail-closed on disclosure**. If the read throws or times out, the state carries the explicit "unknown" line (never "none", which would read as a claim), one `warning` is recorded, and the turn runs as it does today. If the owner scoping, the tier line or the release filter cannot be evaluated, the names are omitted and only the count is shown, or the block says "unknown". A silent "no documents" is the one outcome not allowed.

### Security findings

## Cache, determinism, resume

- **Caching.** No provider cache sits on the decide path (the transport records no cache reads, and the provider documents none; see [the state section](decision-loop-agent.md#what-the-decisions-model-sees-each-iteration)), so changing the state costs no cache. The block is constant within a turn and sits ahead of the iteration lines, so the append-only property holds. It changes between turns only when the set of visible documents changes.
- **Determinism for the suites.** The ordering above makes the string byte-identical for the same inputs, and a conversation with no documents is unchanged, so scenarios 01-03 are untouched by construction. The eval driver seeds its documents from a map (`app/evals/general-next/driver.ts:65, 183-184`), so scripted runs are reproducible.
- **Resume (slice 6).** The list is an input to a decision, not run state. A resume makes no decide call for the paused iteration, and later iterations read the list once on re-entry, so a file added while the person was deciding is seen from then on. Nothing about the list needs rebuilding from events. The release gate (slice 9) runs before the orchestrator on a flipped turn, so on the Anthropic tier the count is built after the person's answer and sees released versions only. An unattended run that the gate stops never builds it.

## Owner rulings

Recorded 2026-10-20; the design above follows them.

- **Q1. Which option?** On every tier other than private, the Decide step sees a **count only** (option 2).
- **Q3. Showing every name on the private tier.** **Overridden toward option 1 there:** every visible document's name, type and size, in a capped list (10 names, 80 code points each, 1,000 characters; beyond the cap, a `+K more documents` count). This replaced the recommended option 4, which is not built.
- **Q2. Names to the Anthropic tier's decisions host.** **No**, as the invariant above. The check compares the run frame's raw tier slot with `'verda'`; everything else gets a count.
- **Q4. Hidden and archived files.** They stay off the list and out of the count; retrieval honours the same flags (#705).

What the rulings do not settle is measurement: whether the list moves scenario 13, whether the count biases the other tiers' routing, and whether the cap fits. The live pass answers those.
