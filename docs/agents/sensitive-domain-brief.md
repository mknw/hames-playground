# Sensitive-domain brief — for sub-agents only

**If you are a coordinator: stop here.** Put the pointer line from
[§3](#3-how-the-coordinator-invokes-this) in the dispatch and read no further.
Do not quote, summarise, paraphrase or paste any part of this file into your own
visible text. The whole point of the indirection is that the domain vocabulary
below is written down _once_, in a place only the executing agent opens.

**If you were handed this path: this is your brief, and you decide whether it
applies.** Your dispatch says only _"read this and apply it if your scope falls
within it"_, plus a deliberately neutral phrase for the work. It cannot say more:
the words that would describe your task accurately are the words the dispatch had
to avoid, which is why they are written down here instead. **Self-selection is the
mechanism** — the coordinator does not know which entry you need, so do not wait
to be told.

---

## How to use this file

1. **Scan the [map](#1-vocabulary-map) against your actual task**, not against
   your dispatch line. Match on the files you are about to touch and the
   behaviour you are about to change. If nothing matches, this file does not
   apply — say so in one line and proceed normally.
2. **Read the sources the matching entries name before you form a plan.** Entries
   are cross-cutting; a task that hits one usually hits two or three. None of this
   is background reading you can substitute with what you already believe about
   this class of problem.
3. **Apply [the handling rules](#2-handling-rules)** to everything you do in
   these areas. They are not style preferences — each exists because its absence
   produced a defect that shipped here.
4. **Land the deliverable as a URL** the way §2 says. Do not merge anything.

The handles (`SD-1`…) are for _your_ navigation and for citing an entry in your
deliverable. Do not expect a dispatch to name one, and do not ask the coordinator
which one applies — asking it to answer that is asking it to read this file.

The map is a **map, not a specification**. It says what a term means here and
where the mechanism lives; it does not certify that the mechanism is correct.
Several entries name a gap rather than a control, one names a control whose
failure policy has never been decided, and one names a doc that is stale against
its own code.

## 2. Handling rules

These apply to every task dispatched against a handle above.

### Verify in source before you assert

Every claim you make about behaviour in these areas carries a `file:line`, and
you have read that line **in this checkout** on this branch. Repo docs — this
file included — are evidence of intent, not proof of current behaviour; several
entries above exist precisely because a doc and the code disagreed. If you
cannot find the line, the correct output is "not found", never a plausible
reconstruction. A claim you cannot cite does not go in the deliverable.

### Adversarial posture, not confirmation

Ask what makes the control fail, not whether it is present.

- **A control that is present but unreachable is a finding.** Two shipped
  defects in SD-5's area were exactly this: a configuration that read like
  protection and matched nothing, and a strictness setting that silently
  switched off the layer beneath it.
- **A test that passes whether or not the code is correct is worse than no
  test** — it manufactures a coverage number. When you add or review tests here,
  mutate the source and confirm the test fails; report _verified by mutation_
  separately from _looks right by reading_.
- **Characterise the current behaviour before changing it.** Pin what the code
  does today, including the parts you think are wrong, so the diff shows the
  behaviour change rather than hiding it.
- **Name failure policy explicitly.** Fail-open and fail-closed are both
  defensible; an _unexamined_ one is the defect. Where the repo has not decided
  (SD-7), surface the decision — do not make it.
- Silent degradation is a finding in its own right: a layer that quietly stops
  running is worse than one that is absent, because the absence is visible.

### Scope

Fix the root cause, not the reported instance: if a report names one call site,
find the others and fix the shared function once. Equally, do not widen a
sensitive-area change into adjacent hardening nobody asked for — file it
instead. `CLAUDE.md`'s code-minimalism ladder applies here like everywhere else,
after you understand the problem rather than instead of it.

### Deliverables and the review gate

The hand-off shape is the `kg-lane-dispatch` skill's; what follows is the part
that binds specifically in these areas.

- **The deliverable is a URL.** Findings land as a **GitHub issue or a PR
  comment**, filed by you, under your own reasoning — a comment on the PR under
  review, or a new issue when there is no PR. Orchestration messages evaporate on
  acknowledgement; the timeline is the durable, attributable record.
- **The owner reviews it personally.** Report back only the URL, a one-line
  verdict or status, gate results, and anything genuinely blocking. Do not send
  the coordinator the substance — it is already at the URL, written for the
  owner, and a coordinator that has to read a domain narrative to relay it is the
  exact cost this file exists to avoid.
- Keep the visible comment short (~500 characters, descriptive, high-level) with
  two escape hatches: high-criticality findings get the detail needed to act on
  them, and a long report rides in a collapsed `<details>` block under the short
  summary in the **same** comment.
- **Cite entries by handle** (`SD-5`, `SD-19`) in the deliverable rather than
  restating them. The owner can resolve a handle; it keeps the comment short; and
  it keeps the vocabulary in one place.
- **Never self-merge, and never merge on green CI.** Green CI is
  self-attestation — the suite proves the author's beliefs about the code, not
  the code.
- **Reviews are coordinator-commissioned, never author-commissioned.** Do not
  pick your own reviewer, and do not ask another agent to bless your work. If you
  believe your change needs review, say so in your report and stop.
- **No periodic status pings.** Message the coordinator to ask a blocking
  question, to escalate, or to report done. Nothing else.

### Gates

The standing acceptance criteria in
[`AGENT-BRIEF.md`](AGENT-BRIEF.md#standing-acceptance-criteria) apply unchanged:
CI green (typecheck · lint · test · build), the coverage floors not regressed
(statements 93 / branches 82 / functions 92 / lines 94, in
`app/vitest.config.ts` — raise by hand, never lower), prettier clean on changed
files, a conventional-commit subject, **no attribution trailers**, `pnpm` only
and always from `app/`, and `pnpm baml-generate` re-run if anything under
`baml_src/` changed.

Two that bite specifically here: the CI format check only globs `app/**`, so a
docs-only change can be prettier-dirty and still go green — run prettier by
hand. And the corpus/ReDoS and chokepoint tests (SD-2, SD-6) are the pins that
make the boundary a control rather than a decoration; a change that makes one of
them pass by weakening it is a regression regardless of the coverage number.

## 3. How the coordinator invokes this

Every dispatch carries this line **verbatim**, whatever the task is about:

```
Read docs/agents/sensitive-domain-brief.md and apply it if your scope falls within it.
```

It goes in every spec unconditionally — not only the ones the coordinator
suspects are in scope. That is the point: the coordinator dispatches _without
knowing_ which domain a task belongs to, the lane self-selects against the map,
and no vocabulary is ever spelled out in coordinator-visible text. A line that
appears only on sensitive tasks would leak the classification by its presence.

In the surrounding spec (the full shape is in the `kg-lane-dispatch` skill):

```
Task <id>: <neutral scope phrase>.

Read docs/agents/sensitive-domain-brief.md and apply it if your scope falls within it.

<what to do, verified against source, with the specifics the lane needs>

Deliverable: post your findings as a comment on <PR #N | a new issue titled "...">.
The OWNER reviews this personally: report back only the URL, a one-line verdict, and
gate results. Do not merge. Communicate via ask / escalation / worker_done only.
```

The neutral scope phrase names the **lane or the artefact**, not the subject
matter: "the guard-review lane", "the inventory agent", "the modules under
`app/src/lib/sandbox/`", "PR #248". Keep coordination narration generic in the
same spirit.

**The standing rule.** The coordinator holds the **path and nothing else**. It
does not read this file, quote it, summarise it, restate an entry in its own
words, or paste any of it into a dispatch, a message, an issue or a PR body — and
it does not choose a handle on the lane's behalf, because choosing one means
having read the map. If a dispatch seems to need more than the line above, the

The same rule runs in reverse on the report back: the URL, a one-line verdict,
gate results, blockers. The coordinator does not need the domain narrative and
