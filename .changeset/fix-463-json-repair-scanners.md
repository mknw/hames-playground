**`repairJson` / `repairJsonTracked`**: the bracketed-literal scanner in the lenient chain is now linear in its input, and the chain refuses input over 16 384 characters (#463). The scanner had three super-linear shapes. An unbalanced `[` or `{` after a colon was scanned to the end of the input at every colon, which is quadratic: ~23 s of CPU at 200 000 characters. A nested literal was re-scanned at every level of a recursive repair, so it cost its depth times its length until the recursion ran out of stack. And nested objects whose innermost value cannot be repaired paid that cost at every nested colon, which is cubic: ~68 s at 16 000 characters and ~10 minutes at 200 000. Each shape now costs about a millisecond at 16 000 characters. One pass decides, bottom-up, whether every literal can be repaired, and a second pass renders only the literals that are parked. Neither recurses. Results are unchanged, with one exception: a differential fuzz of 1.6 million inputs against the previous implementation found no difference in any return value or thrown error, except on literals nested deeper than the old recursion's stack (past ~2 000 levels, depending on JIT state). Those threw `RangeError` and now repair. **Behaviour change for callers**: input longer than 16 384 characters (after trimming) that is neither valid JSON nor recoverable by the unescaped-content strategy now throws a `SyntaxError` that names the length and the limit, even where the lenient chain would have repaired it. It is never truncated. Valid JSON of any length, and the unescaped-content recovery of long payloads, run before the bound and are unaffected. The bound is defence in depth: with the scanner fixed, no step of the function is known to be super-linear. One limit that is not about cost remains: the unescaped-content strategy still recurses, so input it reads several thousand levels deep throws `RangeError`, in about a millisecond, as it did before.
