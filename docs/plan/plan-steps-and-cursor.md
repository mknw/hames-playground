# Structured plan steps with a route tag, and the progress cursor (Design note)

> **Status: design, not built. No code in this PR.** It is the follow-up the owner asked for after [run-7 scenario 14](https://github.com/mknw/hames-playground/pull/606#issuecomment-6447533657) and [#811](https://github.com/mknw/hames-playground/pull/811): the critic of an `actorCritic` route still sees only the user's message and the route's own scope — never the plan — and the plan's steps are free text nobody can mark. This note designs structured plan steps tagged with their route, plus a progress cursor the loop derives from its own records, and says who would read what. It extends [`decision-loop-agent.md`](decision-loop-agent.md), which already names the cursor "a v2 idea" (`docs/plan/decision-loop-agent.md:124`). Source claims were read on `origin/main` at `927996bf` (line numbers are that tree's). A security/privacy review is owed before any slice is dispatched; the boundary analysis below is written for that reader.

## Summary (for the owner, in five lines)

1. Today the plan is free text. The **actor** reads it (`plan_context`); the **critic** never does — it judges against the user's whole message plus #811's route-scope rule, without knowing what the plan says other steps will do; the **decider** sees it only while the `think` record sits inside the last-2 window; the **synthesizer** likewise.
2. Proposed: the planner emits **structured steps** (`route` + `description`), route tags validated against the route table; the **cursor** (which step is current, what is done/failed) is derived by code from the loop's own records — never stored, so a resume rebuilds it for free.
3. Readers: the decider's state gains a static plan block plus a trailing cursor line (preserving the state's append-only prefix cache); the critic gains the plan and the current step, scoped to its route's step; the actor's `plan_context` gains the cursor frozen at child entry; the synthesizer reads plan-with-statuses through the existing records.
4. Safety: no new processor and no new tier crossing — the plan already reaches every one of these models on its own tier today; the pseudonymisation wrapper rewrites any new child-data key wholesale, and its fail-closed path withholds it like the rest.
5. This makes #811's prose rule factual (the critic can see _which_ steps are whose) — but it fixes 14's bind only when a plan exists, and 14's failing run never produced one; the open questions below include whether to nudge the decider toward `think` first.

## The decision, in one paragraph

**Proposed: make the plan a first-class object in the loop.** The planner's output gains structured steps, each tagged with the route that will do it; `decisionLoop` derives a per-step status and a cursor from the route-output records it already builds; the plan-plus-cursor reaches the critic, the decider and the synthesizer in the places each of them already reads, with no new event type, no new LLM role and no new tier crossing. The cursor is derived, never stored: it is a pure function of `latestPlan` and the records, so slice 6's resume rebuild (which reconstructs the records from committed events) reconstructs it with them. #811 gave the critic the rule ("judge only the part of the request this step can do"); this gives it the facts (which steps the plan assigns to which route), which is what turns the rule from advice into something the critic can apply. It is unmeasured by construction — a design note — and the gate re-run of scenario 14 (and 17) is what would settle whether it holds.

## Who sees the plan today

The plan is produced once per turn at most (a guarded `planner` route is withheld once a plan exists, `decisionLoop.server.ts:368-372` and the offered-filter at `:655-658`; `allowReplan` opts a route out). Its only structured facts today are `reasoning`, `plan` (free text) and `n_steps` (`packages/harness-patterns/types.ts:138-146`). From there:

| Reader                                   | What it gets                                                                                                                                     | Where                                                                                                                                                                                                                                                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the planner (`think`) itself             | the user's message as task; the agent map, the earlier conversation and the handoff as its `context` argument                                    | `planner.server.ts:192-201`; wired per-invocation at `decisionLoop.server.ts:787-806` (`agentMap` only for planner routes)                                                                                                                                          |
| `decisionLoop`'s record                  | the plan text, capped, as the `think` route's `result`; `record.plan = { text, steps }`                                                          | `decisionLoop-records.server.ts:355-368` (extractor, over the committed `plan_created` event); `decisionLoop.server.ts:884`                                                                                                                                         |
| the **actor** of a child route           | the plan under the `PLAN` heading inside `plan_context`, plus the handoff and earlier-conversation data blocks                                   | `formatPlanContext`, `planner.server.ts:165-190`; composed at `actorCritic.server.ts:141-148` and `simpleLoop.server.ts:732-736`; passed to the actor only (`actorCritic.server.ts:319-327`)                                                                        |
| the **critic** of an `actorCritic` route | **never the plan.** `intent` = the task (the user's latest message; `data.intent` stays unset) plus #811's host-written `routeScope`             | `actorCritic.server.ts:303-308`; the call is `critic(intent, previousAttempts)` at `:237`; BAML `Critic(intent, attempts)`, `packages/harness-baml/baml_src/actorCritic.baml:352-361`                                                                               |
| the **decider**                          | the plan only while the `think` record is inside the last-2 window, rendered as one `[think] Plan: …` result block                               | `renderState`, `decisionLoop.server.ts:426-458` (`latest = records.slice(-lastN)` at `:430`); `resultBlock`, `decisionLoop-records.server.ts:511-522`. The per-step lines (`stepLine`, `:503-508`) carry route, status and stats — never the plan or a step mapping |
| the **synthesizer**                      | the plan only through the records `compactExecution`'s thread mode reads (`fromPatterns: ['orchestrator']`, `threadTurns: 2`), so again windowed | `general-next.server.ts:385-391`; the design in [`decision-loop-agent.md`](decision-loop-agent.md#synthesis)                                                                                                                                                        |

Two consequences of this shape, both observed:

- **The critic judges blind.** #811's scope line tells it that "other steps do the rest", but it cannot see what the other steps _are_, so it cannot tell whether the part it is about to reject is genuinely nobody's work or merely a later step's. In run-7 scenario 14 it rejected every complete office-data attempt for "index it for this chat" (the host's stash hook, outside the route) and "offer to answer questions" (the synthesizer's) — the plan, had the critic seen it, would have named both as other steps' or the host's work.
- **The decider loses the plan.** After `think` plus two more iterations the plan is out of the window; from then on the decider chooses over per-iteration status lines alone. Run-7 scenario 14's oscillation (office-data ↔ read-documents across five dispatches, no `answer`, three children exhausted) is consistent with deciding without a plan in view — though that run produced no plan at all, see [the limit](#how-this-closes-14s-bind-and-what-it-does-not).

## Proposed shape

### The step

```typescript
interface PlanStep {
  /** 1-based, in plan order. Rendered, and the cursor's unit. */
  readonly index: number;
  /** One of the decisionLoop's route keys. Validated by the loop, not trusted. */
  readonly route: string;
  /** One sentence of what this step does — the planner's own words. */
  readonly description: string;
}
```

`PlanResult` gains an optional `steps?: PlanStep[]` (`packages/harness-patterns/types.ts:138-146`); `n_steps` stays and must equal `steps.length` when both are present (the existing `n_steps` MUST-equal rule in the planner prompt, `packages/harness-baml/baml_src/planner.baml:53`, extended to the new field). Absent `steps` — a plan from an older client, or a planner that did not produce them — every reader falls back to today's behaviour byte-identically. That is the migration story: nothing breaks, the new behaviour switches on per plan that carries steps.

**Status is never model output.** The per-step status (`pending` / `current` / `done` / `failed`) and the cursor are derived by code in `decisionLoop` from the records it already holds — the same pure-function discipline as `stepLine` (`decisionLoop-records.server.ts:503-508`). Matching rule: each record consumes the **earliest unmatched step whose `route` equals the record's route**; a record whose route matches no unmatched step is off-plan and moves nothing; a step whose route never ran stays `pending`; a matched record's own `status` becomes the step's. `answer` and the iteration bound do not move the cursor — they end the loop.

### Who reads what

| Reader          | Gets                                                                                                 | Mechanism                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| the decider     | the plan as a **static block** (steps with their route tags), plus the cursor as a **trailing line** | a fourth section of `renderState` (`decisionLoop.server.ts:426-458`). The plan block never changes within a turn (a replan replaces it wholesale — see open question 4), so it keeps the state's append-only property; the cursor line, the only bytes that change per iteration, is rendered **last**, after "Latest results", so the changing tail stays at the tail. Line format follows `asLine` (`decisionLoop-records.server.ts:524`): one JSON string per step, so a newline inside a step description cannot forge a `User:` line or a heading |
| the critic      | the plan and the current step, scoped to its route                                                   | mechanism below — [Two ways to hand the critic the plan](#two-ways-to-hand-the-critic-the-plan)                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| the actor       | the cursor frozen at child entry, appended inside the `PLAN` block                                   | `plan_context` is formatted once per child run and cannot change between attempts (`actorCritic.server.ts:140-148`); the cursor frozen at entry is exactly right — the child runs one step. Rendered by `formatPlanContext`, so both loop patterns get it from the one formatting site                                                                                                                                                                                                                                                                 |
| the synthesizer | the plan with per-step statuses, through the records it already reads                                | the loop's records already reach `compactExecution`'s thread mode (`general-next.server.ts:385-391`). The derived statuses ride the records' existing fields — the cheapest form is the last record's rendering gaining a `Plan progress:` line; placement is open question 5. No new event type, so `fromPatterns: ['orchestrator']` needs no change                                                                                                                                                                                                  |

### Two ways to hand the critic the plan

| #   | Mechanism                                                                                                                                                                                                      | BAML change                                                                                                                            | Assessment                                                                                                                                                                                                                                                                                                                                   |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | append the current step (its index, route and description, plus one line naming the other steps' routes) to the critic's `intent`, exactly as `routeScope` is appended today (`actorCritic.server.ts:303-308`) | **none** — `intent` is a string argument                                                                                               | Smallest change, but it blends model-written plan text into a field the prompt labels `USER INTENT` (`actorCritic.baml:300`), and the critic's provenance criteria (the `_source` check, `actorCritic.baml:325-331`) read that field as the user's ask.                                                                                      |
| 2   | a new optional `plan_context` input on `Critic` and `CriticThinking`, rendered as its own section after `USER INTENT`                                                                                          | yes — a BAML signature change, regenerate the committed client (`pnpm baml-generate` from `packages/harness-baml/`, commit the result) | Cleaner semantics: `USER INTENT` stays the user's ask, the plan is visibly a plan, and the critic prompt gains one criterion ("the plan assigns this step to this route; a part of the request assigned to another step is not missing"). Costs the regeneration discipline and the two-function (`Critic` / `CriticThinking`) twin surface. |

**Recommendation: option 2.** The critic is the loop's sole exit authority (`actorCritic.server.ts` header; #811); the one call that decides whether a route's work is complete should not receive its scoping facts folded into a field whose prompt meaning is "what the user asked for". The #625 reasoning twin means the new input lands on both functions and the shared `CriticBody` keeps them from drifting.

### Route-tag validation

The planner is told the route keys twice — they are the agent map's line headers (`agentMapEntry`, `decisionLoop.server.ts:227-234`) and the decision options — and the prompt gains the rule "tag each step with the route key that will do it". The loop then validates, deterministically, at record time: a step whose `route` is not a route key of _this_ loop is dropped from the structured steps, the plan degrades to its free-text form for the cursor (readers keep the text), and one `warning` event records it. Refusing the whole plan is the wrong trade: a mistyped tag must not cost the turn its plan. This mirrors the construction-time refusal discipline (`decisionLoop.server.ts:336-345`: a declaration that matches nothing is refused where it is made) — but at runtime the cheap, honest downgrade beats a throw, and the warning makes the downgrade visible rather than silent.

## Why it is safe (guard and view boundaries)

The rule this design is held to: **no text reaches a model through the new path that does not already reach a model on the same tier today.**

- **Provenance of the plan text.** The planner writes it after reading the agent map, the earlier conversation and the handoff — all of which the child-data path already delivers sanitized or fenced: the plan record is built from the committed `plan_created` event, extractors read committed events only and never `content_sanitized` (`decisionLoop-records.server.ts:1-28`, the SD-3 rule), and quoted tool-result bodies keep their ingress fences (the `carry` rule, `decisionLoop-records.server.ts:20-28`, implementation at `:222`). The plan is model-authored text derived from those inputs — the same trust level as the actor's `reasoning`, which the critic already reads attempt by attempt (`actorCritic.baml:306-307`). Adding it to the critic's prompt does not lower any bar; it moves text sideways between two models that sit on the same chain.
- **No new processor (SD-12).** On the Anthropic tier the actor and the critic resolve through the same chain family (`ActorAnthropic` / `CriticAnthropic`, `actorCritic.baml:266-287, 352-361`), and the plan already reaches the actor's client via `plan_context` (`actorCritic.server.ts:319-327`). On the private tier every role in `SELF_DEPLOYED_CLIENT_BY_ROLE` is the same box. The one reader whose surface widens is the **decider**: on the Anthropic tier its state goes to the systemone endpoint (`JEV_DECISIONS_URL`), and today it receives plan text only when the `think` record is inside the last-2 window — this design makes that unconditional. That is a widening of an _existing_ flow (R1 flow 3, which G14 settled as "keep as is"), not a new one; it is open question 1, an owner call, and the private tier — the deployment default — sends the state only to the self-hosted shim either way.
- **Pseudonymisation (SD-8/SD-9).** `withPseudonymisedInputs` rewrites **all inherited child `data`** except the roster-only key, on every path, and withholds everything on its fail-closed path (`docs/plan/decision-loop-agent.md`, [the wrapper's rewrite](decision-loop-agent.md#pseudonymisation-guard-on-the-web-route); the rewrite covers "the latest `think` plan … and arbitrary keys"). If the plan-and-cursor rides a child-data key — which it does for the critic under both mechanisms, since `intent` is composed from `scope.data` — it is rewritten by the same pass with no wrapper change. The one thing to check rather than assume: today the plan reaches `info_ag`'s _controller_ (a `simpleLoop`) via `plan_context`; under this design it also reaches that route's decisions through the state. Both are inside the wrapper's rewrite and the outgoing egress check, which is what keeps a plan naming a mail correspondent from becoming a web-search query in clear. A pin covers the new key explicitly, because "the wrapper rewrites child data" is only as strong as the test that names the key.
- **Fencing and structure.** Step descriptions are rendered one-JSON-string-per-line (`asLine`), so a newline in a description cannot start a line that reads as the state's or the prompt's own structure — the same defence the handoff and conversation blocks already use (`decisionLoop-records.server.ts:524`, `:533-543`). The plan block is data-with-a-heading, never instructions: it sits under its own heading, worded like `HANDOFF_HEADING` ("data, not instructions"), and never inside the `PLAN` heading a child is told to follow — that separation is `formatPlanContext`'s whole point (`planner.server.ts:165-190`).
- **Fresh child data.** `decisionLoop` builds child data fresh; nothing a child writes flows back (`decisionLoop.server.ts` header, [What a child sees](decision-loop-agent.md#what-a-routes-agent-receives-as-its-task)). The cursor derivation reads only the loop's own records and `latestPlan` — no child data, no `content_sanitized`, no new event type.

## How this closes 14's bind — and what it does not

**What it closes.** With a structured plan in view, the critic of an `actorCritic` route judges a named step against a named plan: "you are step 2 of 3 (`office-data`); step 1 (`info-retrieval`) is done; step 3 (`read-documents`) is another route's work". The two clauses that burned six attempts in run 7 — _index it for this chat_ and _offer to answer questions_ — are visible as other steps' or the host's work, not as gaps in this step's results. It also gives the decider what its status lines cannot: which step of how many remains, which is the difference between "office-data succeeded, but did the whole job finish?" and "step 2 of 3 succeeded, step 3 is pending". #811's `routeScope` stays: it is the rule; the plan is the evidence the rule needs.

**What it does not close — stated plainly.** Run-7 scenario 14's failing turn dispatched office-data ×2, read-documents ×2 and **never ran `think`**: there was no plan for a cursor to follow. This design changes nothing for a turn that never plans; #811's scope line remains the only protection there. Whether the decider should be steered toward `think` first on multi-part requests is open question 3 — it is a prompt lever with run-6's counter-evidence attached (`think` chosen six of six iterations once offered freely; `decisionLoop.server.ts:59-62`), which is exactly why the planner-withholding guard exists and why the lever must be measured, not assumed.

## Options considered

| #   | Shape                                                                               | Rejected because                                                                                                                                                                                                                                                      |
| --- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | structured steps from the planner, cursor derived from records                      | **chosen.** The model already knows the route names (its agent map); validation is deterministic; the cursor costs no state.                                                                                                                                          |
| 2   | keep the plan free text; code parses the numbered list and infers routes by keyword | a parser guessing "which sentence is about the office" is the failure mode this agent already paid for in prose (the critic's whole-message intent); and an inferred tag that is wrong is worse than one that is absent.                                              |
| 3   | store the cursor in loop state and persist it on the records                        | slice 6 rebuilds records from committed events on a resume; a stored cursor is a second copy that can disagree with the rebuilt records. Derived-from-records is the same discipline as "one projection function builds an entry both live and on replay".            |
| 4   | mark the cursor inline in the plan block ("→ 2. office-data …")                     | mutates the plan block's bytes every iteration, breaking the state's append-only prefix-cache property for the whole tail; a trailing cursor line costs the same information and touches only the tail.                                                               |
| 5   | give the critic the whole `plan_context` (plan + handoff + conversation)            | the handoff carries quoted tool-result bodies — data the critic does not need and the actor already has; the minimal disclosure is the plan and the cursor, and every additional block in the critic's prompt is more text a critic can be talked out of position by. |

## Tests: which layer, and what each pins

Per [`docs/testing/pyramid.md`](../testing/pyramid.md) — layer 1 carries the pins and gates the merge; the live layers measure, they do not gate.

- **Layer 1 (unit, `app/src/__tests__/`, CI gate):**
  - the cursor derivation as a pure function: each record consumes the earliest unmatched same-route step; off-plan records move nothing; failed records mark `failed`; `answer` and the bound leave the cursor where it is. Mutation: match records to the _latest_ same-route step instead — a route that ran twice must not consume two steps out of order.
  - the decider's state: plan block static across iterations within a turn, cursor line last and changing; no plan → byte-identical state to today. Mutation: render the cursor inline in the plan block (must break the append-only pin, not merely look different).
  - route-tag validation: an unknown tag drops the step, degrades to free text, emits one `warning`. Mutation: accept the unknown tag.
  - the critic's input, for both functions: the plan and current step arrive in their own section, `USER INTENT` unchanged; no plan → the rendered prompt is byte-identical to today's. Mutation: fold the plan into `intent`.
  - the actor's `plan_context`: the cursor line is inside the `PLAN` block, frozen at child entry; handoff and conversation stay outside it. Mutation: move the cursor into the handoff block.
  - the pseudonymisation pin: a `general-next`-shaped wrapper rewrites the new child-data key and withholds it on the fail-closed path (extends the existing wrapper pins rather than adding a seam).
  - the SD-3 pin: a fixture carrying both a sanitized `tool_result` and a `content_sanitized` event with a synthetic raw span — the derivation and every renderer read the former and never the latter.
- **Layer 2 (app-path e2e, `app/e2e/`):** a scripted two-route turn where the child is an `actorCritic` route whose request includes a clause only a _later_ step can do: the critic sees the plan and the cursor and accepts the route's share. Mutation: drop the plan from the critic's input — the acceptance must degrade to the #811 behaviour, not to a rejection.
- **Layer 4 (the gate, `pnpm eval:harness`):** scenario 14 and 17 at the gate re-run, plus the existing screen-on-the-tier and planner-plan-shape scenarios — a plan-shape regression (steps not produced, tags not validated) must surface there. Per the run-7 discipline: no retries; the owner's no-retries ruling stands.

## Open questions for the owner

1. **The Anthropic-tier decide disclosure.** Making the plan unconditional in the decisions state widens R1 flow 3, which G14 settled as "keep as is" — on the Anthropic tier the state (plan included) would reach the systemone endpoint on every iteration instead of only while `think` sits in the last-2 window. The private tier is unaffected. Accept the widening, or keep the plan windowed on non-private tiers?
2. **Unknown route tags.** Proposed: drop the step from the structured shape, degrade to free text, warn. The alternative — refusing the plan and withholding it — spends the turn's plan on a typo. Confirm the downgrade.
3. **The un-planned turn.** 14's failing run never produced a plan, so the cursor never fires there. Should the decider be nudged toward `think` first on multi-part requests (a route-description or criterion clause, to be measured at the gate), or is #811's scope line the accepted answer for un-planned turns?
4. **Replans.** With `allowReplan` opted in, a new plan replaces `latestPlan` — does the cursor reset to step 1 of the new plan (records unmatched so far) or should completed work from the old plan carry over? The proposed default: reset, and mark nothing from the old plan.
5. **Synthesizer placement.** Plan-with-statuses inside the last record's rendering (cheapest, rides the existing thread-mode read) versus a dedicated derived block the renderer knows about. The note recommends the former; the choice affects only rendering, not the data.
6. **`answer` awareness.** The decider's `answer` criterion (`general-next.server.ts:372-373`) already carries failure-reporting guidance. Should it also see "steps 3 of 3 remain" — making early `answer` a visible trade — or is that one clause too many for a 4B-class classifier to weigh?
