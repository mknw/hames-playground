HITL events and the derivation (#433, slice S1). Nothing emits the new events yet: asking, pausing and the answer-bound `resumeHarness` arrive in later slices.

- **Two new event types**, `hitl_request` and `hitl_response`, with their payload types `HitlRequestEventData` and `HitlResponseEventData` (both `v: 1`) and the types they use: `HitlOption`, `HitlFlag`, `HitlUnattended` and `HitlDecidedBy`. Both are always committed, so no `commitStrategy` (`on-success` after an error, `last`, `never`) drops them. `approval_request` and `approval_response` stay in `EventType`, marked `@deprecated`. **Breaking for exhaustive consumers**: `EventType` gains both new members, so a `Record<EventType, …>` or an exhaustive `switch` over it stops compiling until it handles them.
- **`readHitl(ctx)`** (with the `HitlState` type) is the one reader. From the current run, meaning the events after the last `user_message`, it derives `pending`, the blocking requests with no response in raise order, and `answers`, the replay journal. An answer enters the journal only if it names a blocking request of the run, carries that request's kind and key, and chose an available option of it. The journal is keyed by kind, key and the set of option ids. Legacy `approval_*` events are never read, so a stored `approval_response { approved: true }` answers nothing.
- **`answerOf(view, key)`** returns the current run's answer stored under `key`, in the `${kind}:${key}` form both events carry. It reads the view's unfiltered log, so a narrowed `viewConfig` cannot hide an answer. It returns `undefined` when two different decisions share the key.
- **Only core writes HITL events.** **Behaviour change**: `createEvent` and `trackEvent` throw for `hitl_request` and `hitl_response`, whatever `trackHistory` says. `commitEvents` and `chain()` drop any event of those two types that core did not create, and log a `console.warn` for each. No other event type is affected.
- **Metadata-only rendering.** `serialize()` and `serializeCompact()` render `hitl_request` as `decision requested: <kind> [<requestId>]` and `hitl_response` as `decision: <kind> → <choice | none> (<by>)`. They never render the question, summary, options, payload reference, principal, flags or resolution. **Behaviour change**: `approval_request` and `approval_response` now render as `legacy approval event` instead of a JSON dump of their payload. That includes the `approval_response` that `resumeHarness(…, approved)` still appends.
